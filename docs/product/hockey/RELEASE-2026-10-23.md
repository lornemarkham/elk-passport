# Hockey Night — release candidate for Friday 23 October 2026

**Branch:** `feature/hockey`, a fast-forward of GitHub `main` (`b6f571a`)
plus this mission's commits. Nothing here has been pushed, deployed, migrated
or applied to any real project.

**Short version.** Hockey Night was already built, and its code is already
in production: `/hockey` on gohaveaday.com redirects to sign-in, and its API
answers `401`. What stands between it and coworkers' phones is **not code**.
It is the database: the Hockey migration has to be in the production Supabase
project, and nobody has confirmed that it is. This mission added the one
missing requirement (the host chooses what's in a night) and the "Now go have
another" ending, then re-verified everything with real accounts.

## 2. Architecture — a conflict, named, not resolved

The brief says _reuse Conference's foundation; do not introduce a second
competing group framework._ The repository already says something different:

- Hockey has had its **own** foundation (`passport_occasion_*`: membership,
  hashed single-use invites, RLS) since 2026-10-11. Conference has
  `passport_conference_*`. Boards have `passport_board_*`.
- **ADR 009 (2026-10-12)** chose a fourth thing, `passport_adventures`, as
  _the_ one group foundation, and says Hockey and Conference "can adopt it
  incrementally … without blocking their releases". Doctrine §15.12 records
  that as partly answered.
- Conference's own migration explains why it did not use Hockey's tables;
  ADR 009 explains why it did not use Conference's (plaintext invite tokens,
  the whole conference in one jsonb).

**What this release does:** it keeps Hockey on its existing, attacked and
already-deployed foundation and **adds no new tables**. That introduces no
new framework. Moving Hockey onto Conference's tables by Friday would rewrite
the most-verified part of the product two days before people rely on it, and
would move it _away_ from the foundation ADR 009 chose.

**Needs your decision, not mine:** whether Hockey moves onto Adventures
(ADR 009), onto Conference (this brief), or stays. Until then Passport has
four group stores, which ADR 009 already calls visible and documented.

## 3. What this mission built (smallest safe plan)

Two gaps against the brief, both closed without a migration:

1. **The host chooses what's in a night.** Five modules — _Where we eat_,
   _Where we meet_, _When we leave_, _Sealed picks_, _Stupid questions &
   dares_ — ticked on the start form and changeable by the host on the night
   under **What's in tonight**. Who's in, the conversation, the Cup and the
   recap are the night itself and are always on.
   - Stored as `details.modules` on `passport_occasions`, a column the host
     could already update under the existing RLS policy and column grant.
     Nights without it have everything on, so existing nights are unchanged.
   - `composeNight` leaves a switched-off module's questions out, so the
     server refuses answers to them exactly as it refuses questions that do
     not exist. The toy box is refused too. Nobody's answers are deleted;
     turning a module back on brings them back.
   - Run it back starts with last time's modules.
   - Found and fixed by the new browser test: with picks off, the section
     still said "Your picks — sealed until puck drop" over nothing, because
     it also holds _Ask the group_. Two quick taps on the host's toggles also
     undid each other.
2. **"Now go have another."** The morning-after card leads with that, keeps
   _Start the next one_, and adds _Or not hockey at all: go have a day_
   (`/discovery`).

**Deliberately not done**, and why:

- **Choosing a venue.** Everything that makes the night useful before puck
  drop — the dinner list, distances, the meeting spots — is measured from
  Rogers Arena, and the start form already says so. A watch-party venue
  needs a venue picked from Atlas with observed coordinates. That's a real
  next step, but not for this week.
- **Activities near the arena.** The dinner vote offers Atlas's Eat & drink
  near the arena (bars included). Other activities are not offered: none of
  the night's questions asks for one, and adding one would be inventing a
  requirement.
- **Live NHL integration and richer memories**, optional per the brief.
- **Writing the plan into an Adventure or Go Have a Day.** The winning place
  and leaving time show as _The plan_ on the night; they are not exported.

## 5. Migrations and environment variables

**This mission adds no migration and no environment variable.**

The one Hockey migration that must be in production is the existing
`docs/product/hockey/migration.sql` (10 tables, 8 functions, 25 policies,
explicit grants), with `preflight.sql` → `migration.sql` → `verify.sql`. It
is idempotent: safe to run whether it was applied before or not. If an older
copy was applied before its grants were written, `fix-grants.sql` is the
corrective, and running `migration.sql` again does the same.

It is **not** in `supabase/migrations/`, which is a shared contract owned by
`passport-domain`. Proposal for that lane: land it byte-for-byte as
`supabase/migrations/20261011000000_passport_occasions.sql` after it is
applied, the same way Conference's migrations landed.

Environment variables on Vercel `elk-passport`, unchanged from what

## 6. Integration and deployment — exact steps (yours; nothing here is done)

Production deploys from GitHub `main` (Vercel is Git-connected).

1. **Fetch and fast-forward** (on the Mac):
   ```
   git fetch metatron:passport/main feature/hockey
   git checkout main && git pull --ff-only origin main      # expect b6f571a
   git merge --ff-only FETCH_HEAD
   ```
   If `main` has moved past `b6f571a`, merge instead of fast-forwarding and
   re-run the gates. Don't push yet.
2. **Database first** — Supabase dashboard → project `frllwwxesxbmmaadzfaf` →
   SQL editor. **Never `supabase db push`.**
   1. Is it already there? `select to_regclass('public.passport_occasions');`
      (`null` means it never was.)
   2. Run `docs/product/hockey/preflight.sql`.
      - If 2.1 was `null`: every row must be `OK`.
      - If 2.1 was **not** `null`: the three "nothing of ours exists yet"
        rows will say `STOP` by design (it was applied before). Every
        **other** row must be `OK`. Then continue: the migration is guarded
        and a re-run only adds what is missing, including the grants
        (`PRODUCTION-READINESS.md` §14).
   3. Run all of `docs/product/hockey/migration.sql`.
   4. Run `docs/product/hockey/verify.sql` → 10 rows, all `OK`.
   5. Run `docs/product/hockey/verification/grants-check.sql` → all `OK`.
3. **Auth settings** — Authentication → URL configuration → Redirect URLs
   include `https://gohaveaday.com/**` (and `https://elk-passport.vercel.app/**`
   if links are sent from there). Decide whether email confirmation is on; if it
   is, custom SMTP must be configured or coworkers' confirmation emails may
   never arrive.
4. **Push** `main` → Vercel builds and deploys it. Instant Rollback is the
   undo.
5. Run §7 **before** sending a single invitation.

**Levers if something goes wrong**, smallest first: the host revokes a link or
removes a person; `disable.sql` stops anyone starting or joining (deletes
nothing; `enable.sql` undoes it); Vercel Instant Rollback; `rollback.sql`
(refuses while any night exists).

## 7. Production verification checklist

Do this on gohaveaday.com with your own account and a second real person on a
phone. Allow about 15 minutes. Anything failing → `disable.sql`, invite nobody.

**Alone (≈5 min)**

- [ ] Signed out, `/hockey` → sign-in page; `/hockey/api/occasions` → `401`.
- [ ] Signed in, `/hockey` shows the start form **with the five "What's in it"
      rows** (proves this build is live).
- [ ] Untick _Sealed picks_ → **Start it** → the night opens with no
      "Your picks" section. **An error here means step 2 (database) did not
      happen.**
- [ ] _What's in tonight_ (bottom of the page) → tick _Sealed picks_ → "Your
      picks" appears.
- [ ] **What's near the arena?** → real places (Chambar, Shark Club, …) with
      "straight line" distances. Nominate one.
- [ ] **Make a link** → it starts `https://gohaveaday.com/hockey/join/`.

**With a second person on a phone (≈10 min)**

- [ ] They open the link signed out → "Somebody wants you there.", and nothing
      about the night or who's going.
- [ ] They sign up through it (if confirmation is on, they open the email,
      ideally on another device) and **land back on the invitation**, not
      Discovery.
- [ ] Name → **I'm in** → both rosters show both of you within ~5 s.
- [ ] Both vote on dinner and on leaving at the same moment → each sees the
      other's.
- [ ] They post in **The night**; you react; they see the reaction.
- [ ] You make a score pick; they can't see it until they've made theirs.
- [ ] They have no guest list and no _What's in tonight_.
- [ ] Open the same invitation link in a third browser with a third account →
      "This link has done its job."
- [ ] Remove them → their page leaves within a few seconds.

When all of that passes, make one link per coworker in the guest list.
On the night, after the final horn, use **Call it** to record results.
Passport has no scores feed.
